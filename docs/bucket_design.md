基于固定启发值桶的前沿平台检测机制

1. 原方案的问题

早期方案主要跟踪搜索器当前弹出状态所在的启发值层 (h)，并根据该层连续出现的时间、生成状态数和展开状态数判断平台期。这种方法隐含假设：平台期内相同的 (h) 会连续出现。

实际搜索并不满足这一假设。Open List 中通常同时存在大量相近启发值的状态，弹出序列可能在 (h=10\sim20) 之间频繁抖动。例如某个真正活跃的 (h=15) 层可能长期反复出现，但被其他层穿插。旧方案会在 (h) 改变时重新统计，使任何单层都难以积累足够证据。

此外，短暂出现的更小 (h) 可能很快进入死端。它虽然重置了全局最佳 (h) 的停滞计数，却不代表搜索取得了持续进展。因此，仅依赖当前层或全局最佳 (h) 都容易受到这种暂时性震动影响。

2. 新的固定桶机制

新方案为不同的启发值维护独立统计桶。状态即使非连续出现，只要具有相同的 (h)，其生成和展开活动都会累计到同一个桶中。这样可以识别“长期反复出现、但在弹出序列中并不连续”的真实活跃层。

系统最多维护16个桶。启发值首先按精度量化，然后映射到固定大小的哈希表中；当出现超过16个不同启发层时，淘汰最久未出现的桶。该设计具有两个工程优势：

内存开销为严格的 (O(16))，不会随搜索状态数增长；

每次生成或展开状态只需进行一次固定容量查找并更新少量计数器，复杂度可以视为常数。

每个桶分别记录：

最近窗口内该层产生的状态数 (O_h)；

最近窗口内该层展开的状态数 (E_h)；

自该层上次请求以来的生成和展开数量；

最近一次出现和请求的位置；

当前代表状态；

连续增长、平静和不活跃的窗口数。

定义该层的前沿增长率为

[
R_h=\frac{O_h}{E_h},
]

净增长量为

[
G_h=\max(O_h-E_h,0).
]

当同一启发值层产生状态的速度持续高于被搜索器消耗的速度时，该层状态会在 Open List 中不断积压。这表明启发函数难以进一步区分该层内部的状态，因而可视为一种局部前沿平台。

3. 当前参数设计

一次统计窗口包含8192次状态展开，最近4个窗口共同构成约32768次展开的滑动观察区间。这样既能跨越短期 (h) 抖动，又不会让旧数据长期支配判断。

一个桶被认为处于有效增长平台，需要同时满足：

最近展开数不少于4096；

最近净增长不少于1024；

(O_h/E_h\geq1.05)；

上述条件连续满足2次分析。

其中，绝对数量限制用于排除偶尔出现的稀疏启发层；1.05的比例限制要求该层确实存在持续积压；连续确认两次用于过滤单窗口尖峰。

如果一个层连续4个分析窗口不再增长，则结束当前平台事件；如果连续4个窗口没有新状态加入，则进一步清除该层的冷却状态，使其未来重新出现时可以作为新的平台事件处理。这个机制相当于为启发层提供生命周期划分，但不会因其他 (h) 值短暂插入而立即丢失统计。

4. 重复请求与请求节流

同一个启发层没有终身请求次数上限。一次请求后，该桶的“新增证据”计数清零，但历史活跃状态仍可继续保留。若该层持续活跃，则在满足以下条件后可以再次请求：

距上次请求至少经过500000次全局展开；

该层又累计至少8192次展开；

自上次请求后又形成至少2048个状态的净增长。

因此，长期反复出现的困难层可以多次获得LLM帮助，而不会因为早期请求过一次就永久失去请求资格。同时，较大的同层间隔可以避免一个高频启发层垄断全部LLM资源。

系统还设置100000次展开的全局请求间隔，用来限制不同触发器之间的总体请求频率。每次分析最多考察优先级最高的3个候选层，默认只实际发送1个请求。候选层依次按照净增长量、总活动量、距上次请求时间以及较小的 (h) 排序。

5. 改进效果

新机制将判定依据从“当前连续出现的启发值”改为“各启发层在一段搜索过程中的累计流入和流出”。因此：

不会因 Open List 弹出序列中的频繁 (h) 抖动而反复清空统计；

不会因短暂获得更优 (h) 后迅速回退而遗漏真实平台；

可以分辨偶尔出现的启发层与持续积压的活跃层；

允许困难层在获得新证据后重复请求；

保持固定内存和极低的热路径计算开销。

本次运行在122880次展开时产生了 frontier_growth_plateau 请求，说明新机制已经能够从交错的启发值序列中积累出稳定的层级增长证据，而不再依赖同一 (h) 连续出现。

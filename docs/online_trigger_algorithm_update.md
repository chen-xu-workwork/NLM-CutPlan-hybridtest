# 在线 LLM 触发算法修改摘要

## 修改目标

本项目只负责利用 LLM 改善在线搜索，不改变强化学习模块。LLM 生成的动作前缀被视为额外搜索提示：原生搜索继续运行，合法前缀对应的状态仍由搜索器评估并插入 Open List。因此，即使 LLM 请求失败或生成质量较差，也不应阻塞或替代原有搜索路径。

在线主线以尽快找到首个合法解为目标，而非证明燃料代价最优。搜索器使用 eager greedy best-first search，按剩余 `h` 组织 Open List；真实动作代价仍沿父链累计并写入最终计划统计，但不再通过 `g+h` 阻止合法的非最优 LLM 前缀优先接受探索。

## 与旧方案的主要区别

旧触发器周期性抽取 Open List 前若干状态，通过 h、f 的离散程度判断平台期，同时为所有搜索状态维护额外的父链信息和 frontier 副本。这种方法在状态达到数百万、数千万时会产生明显的时间与内存开销，而且大量相同最优 h 状态可能使判定退化为“搜索足够久就必然触发”。

新方案不再扫描或复制 Open List，而是使用固定容量表按 h 聚合近期窗口中的“新插入条目数”和“实际展开状态数”。各 h 的统计相互独立，因此 Open List 弹出的 h 即使频繁交错，也不会清空已有证据。当某个 h 的新增速度持续快于展开速度时，说明该层正在膨胀、搜索难以排空，因此将其判定为增长型平台期：

```text
平台增长率 = 同 h 新增数 / 同 h 展开数
```

平台必须满足最小样本、绝对净增长、增长率阈值，并连续多个窗口成立才会触发，避免把短暂波动或小样本误判为平台。

## 触发协调

- 所有触发共享公共请求间隔；同一 h 另有更长的独立间隔，且必须在上次请求后积累新的增长证据。持续拥堵本身就是启发式困难的信号，因此不再设置同层每事件或生命周期请求次数上限；长期活跃层可以按独立间隔持续获得机会，正式运行仍由问题级总预算限流。
- 连续多个平稳窗口结束当前平台事件；连续无新增还会解除旧层 cooldown，使未来重新出现时按新事件处理。
- 每个请求槽从近期净增长和活动量最高的若干 h 中选择代表状态；默认只提交一个，也可显式配置为小批次。
- 平台期、祖先停滞和全局 best-h 停滞共享最小请求间隔，避免多个规则集中提交。
- 全局停滞在一次停滞过程中只触发一次，只有 best-h 再次改善后才重新开放。
- 祖先停滞改为低频抽样，并复用搜索节点已有的 parent 指针，不再保存逐状态父链副本。

## 开销与搜索语义

普通热路径只增加一次固定容量 h 查找和常数次计数；平台汇总、候选排序、祖先检查和诊断日志都按较大的展开间隔执行。h 表固定为 16 个桶、每桶最多 8 个窗口，运行中不扩容。旧的逐状态探针、状态信息表和 frontier `multiset` 已移除，触发器内存不再随搜索状态总数线性增长。

正式在线模式采用异步旁路：请求状态照常展开，LLM 返回后才从该状态逐步应用合法动作，并把产生的状态交回普通 Open List。搜索器仍按 greedy `h` 顺序决定是否探索这些状态；若 LLM 前缀没有改善启发式，它不会被特殊强制展开。纯 eager-greedy 搜索仍作为对照基线。

触发监控复用 Open List 已有的弹出键，不重新计算启发式：A* 兼容模式的键为 `[f,h]`，satisficing 主线的键为 `[h]`，两者都直接读取最后一个分量。因此切换搜索目标不会引入逐展开分配或额外启发式计算。

在不接入 LLM 的标定阶段，系统仍会完成触发、状态恢复为 PDDL 和请求对象构造，但使用 log 通信模式，不进行 HTTP 推理，以便先独立调节触发频率和分布。
